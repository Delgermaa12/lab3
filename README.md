## SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 200мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

**Босго сонгосон үндэслэл:** Серверт /pay endpoint дээр ~5% алдаа зориудаар суулгасан тул 8% гэдэг бодит, боломжийн босго юм. /cart/add нь localhost дээр маш хурдан хариулдаг тул 200мс нь тохиромжтой, шалгах чадвартай (ямар ч машин дээр биелэх боловч бодит утга шалгах) босго.

**Error budget тооцоо:** 2 минутын цонхонд 90% availability гэдэг нь 10% буюу 12 секундийн "эвдрэх эрх" гэсэн үг (2 мин = 120 сек, 120 × 0.10 = 12 сек).

slo-test үүүсгэж түүнийгээ ажлуулсан бөгөөд үр дүнгийн txt файл нь result/pass.txt дотор байгаа бөгөөд result дотор мөн тухайн үеийн ажлуусан үеийн screenshot оруулсан байгаа. Үүний ажлуулсны дараагаар cart/add нь 1.56мс хариулсан бөгөөд лабораторийн бичсэн анхааруулгатай яг таарч байсан тийсээс 200мс босго нь одоогийн бодит гүйцэтгэлээс (1.56мс) хэт өндөр тул PASS/FAIL ялгаа хийхгүй сул threshold.

slo-test.js-даа /report endpoint зориулаад 4 дэх threshold нэмсэн бөгөөд http_req_duration{name:report}': ['p(95)<450'],   энэ мөрийг нэмсэн байгаа тэгээд хадгалсны дарагаагаар ахин ажиллуулж түүнийхээ үр дүнг passv2.txt дотор хадгалсан бөгөөд screenshot мөн авсан байгаа passv2's screenshot.png гэсэн нэртэй байгаа. энэ ажиллагааны үр дүн нь /report-ийн p(95)=392.06мс байсан бөгөөд энэ нь 450мс-ийн доор, гэхдээ 200мс-ээс их учраас бодит саатал зөв хэмжигдэж, threshold-той нь утга учиртай харьцаж байгааг харуулсан гэж бодож байна (энэ бол /cart/add-ийн адил "сул threshold" биш, жинхэнэ шалгуур болж байна).

## Mini chaos availability scenario туршилт:
Үүгээрээ би өөрийн серверийг тест хийх явцдаа зориудаар унагаах зорилготой байгаа.

Хамгийн түрүүнд slo-test.js доторх duration  хэсгийг нь 1m байсныг 2m болгон өөрчлөхөөс эхэлсэн байгаа
export const options = {
  vus: 20, duration: '2m',.....

  үүний дараагаа энэ даалгаврын гол зорилго болох тест хийж байх явцдаа өөрийн ажлуулж байгаа серверээ унагааж ахин ажлуулахад тест маань ажилласаар байх хэрэгтэй байсан. Миний хувьд би 2 удаагаар серверээ унагаасан бөгөөд түүнийхээ үр дүн маань result/chaos.txt файл дотор үр дүн нь байгаа мөн chaos's screenshot.png гэсэн файлыг хамт хийсэн байгаа.

  гаралтын үр дүн нь:
✗ checks: rate>0.90 → 81.30%  (FAIL)
✓ http_req_duration{name:cart}: p(95)<200 → 1.58ms  (PASS)
✓ http_req_duration{name:report}: p(95)<450 → 386.94ms  (PASS)
✗ http_req_failed{name:pay}: rate<0.08 → 21.85%  (FAIL)

Performance threshold-ууд (cart, report) хэвээрээ PASS хэвээр үлдсэн, учир нь зогсолтын үед хийгдсэн хүсэлтүүд latency биш харин алдаа (failed) гэж тооцогддог тул latency статистикт нөлөөлөөгүй.

Бодит availability = амжилттай хүсэлт / нийт хүсэлт = 4710/5793 = 81.3%

Энэ бол SLO-т цагаар тооцсон 12 секундийн budget-ээс өөр гарч байна, учир нь 
k6-ийн checks нь цагийн биш хүсэлтийн хувиар хэмжигддэг. Сервер унасан үед 
хүсэлт агшин зуур (connection refused) буцдаг тул зогсолтын 1 секундэд хэвийн 
үеийнхээс олон хүсэлт "амжилтгүй" болж бүртгэгдэнэ, ялангуяа /report шиг 
200-400мс хүлээдэг endpoint хэвийн үед секундэд цөөн хүсэлт хийдэг байсан бол 
зогсолтын үед тэр хугацаанд илүү олон хүсэлт (алдаатай) шидэгддэг.

Reliability threshold (http_req_failed{name:pay}) мөн FAIL болсон, учир нь 
сервер унасан үед /pay-ийн хүсэлт бүр л амжилтгүй болдог. Ингэснээр нэг эвдрэл 
(сервер унах) хоёр өөр SLO-г (availability, reliability) зэрэг зөрчиж байна. 
Эдгээрийг тусгаарлахын тулд availability SLI-г зөвхөн "сервер холбогдож байгаа 
эсэх" дээр, reliability SLI-г зөвхөн "сервер ажиллаж байх үеийн алдааны хувь" 
дээр тусад нь тооцож болно (жишээ нь: connection error-уудыг тусад нь 
шүүж гаргах).

## Threshold зориуд эвдэж fail болгох хэсэг:

Үүн дээр тусдаа slo-test-fail.js гэсэн slo-test.js copy файл үүсгэсэн бөгөөд түүн дээрээ тестээ санаатайгаар FAIL болгож, CI/CD дээр FAIL хэрхэн харагддагийг үзэх хэрэгтэй байсан.

Тиймээс би slo-test-fail.js файлын /report-ийн threshold эвдэрхий болгох зорилготойгоор 
'http_req_duration{name:report}': ['p(95)<100'],  
гэж 450-ийг 100 болгосон байгаа учир нь /report эндпоинт 200-400мс хооронд хариулдаг тул.

Үүний дараагаар ахин тест хийсэн бөгөөд /report хэсэг маань файл заасан ч гэсэн  exit code маань буруу гараад байсан. Энэ хэсгийн fail's screenshot.png дотор би ss хийж result фолдерт оруулсан байгаа. exit code дээр алдаа гарсан нь гаралтад exit=0 гэж бичигдсэн байгаа ч, k6 өөрөө threshold зөрчигдсөн тул бодитоор 0 биш exit code буцаах ёстой. учир нь миний энэ тест ажлуулахдаа ашигласан комань маань k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=$?" энэ байсан бөгөөд энд $? нь сүүлийн командын exit code-ыг харуулж байгаа, k6-ийн биш! tee файл руу амжилттай бичсэн тул 0 буцаадаг. гэхдээ k6 өөрөө FAIL болсон эсэхээс үл хамааран. Тиймээс үүнийгээ pipestatus ашиглан засах гэж оролдсон байгаа. 

k6 run slo-test-fail.js 2>&1 | tee result/fail2.txt
echo "exit=${PIPESTATUS[0]}"

энэ командыг ашиглан засах гэж оролдсон бөгөөд үр дүнгийн report/fail2.txt болгон хадгалсан. 

Үр дүнд нь: 
 FAIL мөр:  ✗ http_req_duration{name:report} 'p(95)<100' p(95)=388.99мс

k6-ийн буцаасан exit code: 99 (0 биш) CI pipeline яг энэ exit code-оор 
build-ийг унасан гэж таньж, зогсоодог. 

Анхны оролдлогод `echo "exit=$?"` ашигласан боловч энэ нь k6-ийн биш 
pipe дэх сүүлийн команд (`tee`)-ийн exit code-ыг харуулж байсан (үргэлж 0). 
${PIPESTATUS[0]} ашигласнаар k6-ийн жинхэнэ exit code (99)-ыг зөв авч чадсан.

## Дүгнэлт

Энэ лабораторид сценарио бичихээс эхлээд бодит k6 threshold болгон кодчилж, 
эцэст нь chaos туршилтаар шалгах хүртэлх бүх шатыг өөрийн биеэр туулсан. 
Хамгийн хэцүү байсан хэсэг бол SLO-гийн босго тоог сонгох алхам байсан учир 
нь localhost дээрх /cart/add шиг маш хурдан endpoint-д 200мс шиг сул босго 
тавихад PASS/FAIL ямар ч ялгаа гаргахгүй "утгагүй" threshold болдгийг олж 
мэдсэн бөгөөд, харин /report-д 450мс тавихад бодит гүйцэтгэлтэй (392мс орчим) 
харьцуулах боломжтой утга учиртай threshold болсныг харьцуулж ойлгосон. Мини 
chaos туршилт миний availability сценариог зарим талаараа баталж, зарим 
талаараа үгүйсгэсэн: сценариод "сервер унасан үед бэлэн байдал буурна" гэж 
таамагласан нь зөв байсан ч, бодит унасан хувь (81.3%) нь миний SLO-д зааж 
өгсөн 90%-аас доогуур гарсан тул SLO хэт өөдрөг байсныг харуулсан. Мөн цагаар 
тооцсон 12 секундийн error budget болон бодит хүсэлтээр тооцсон availability 
хоёрын хооронд ялгаа их байгааг олж харсан нь надад хамгийн том ойлголт өгсөн 
хэсэг бөгөөд учир нь k6 checks metric нь цагийн биш харин хүсэлтийн тоогоор 
тооцогддог тул сервер зогссон богино хугацаанд ч гэсэн олон хүсэлт нэг дор 
"алдагдаж" болохыг харлаа. Мөн нэг эвдрэл (сервер унах) availability болон 
reliability гэсэн хоёр өөр SLO-г зэрэг зөрчиж болохыг ажигласан нь, SLI-гээ 
илүү нарийн тусгаарлаж тодорхойлох хэрэгтэйг ойлгуулсан. Threshold-оо зориуд 
эвдэх алхамд exit code-ын талаар анх andуулаагүй нэг гол алдаа гаргасан
pipe дотор `$?` ашиглахад k6-ийн биш харин сүүлийн командын (tee) exit code 
буцдаг болохыг олж мэдээд, `PIPESTATUS[0]` ашиглан засварласан. Энэ бол CI/CD 
pipeline бодитоор яаж тест унасныг мэддэгийг ойлгоход маш чухал сургамж болсон. 
Ерөнхийдөө энэ лаб надад "Сценарио ->  SLO ->  Threshold" гэсэн онолын шугамыг 
жинхэнэ код, жинхэнэ тоо дээр туулж үзэх боломж өгсөн бөгөөд SLO гэдэг 
зөвхөн тоо биш, харин ард нь бодит үндэслэлтэй байх ёстойг ойлгосон.
